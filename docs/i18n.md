# Translations

Every string a user sees, in the web app, the mobile app and the server's emails, comes from `packages/i18n` (`@s10n-base/i18n`), built on [i18next](https://www.i18next.com/) and [react-i18next](https://react.i18next.com/). English is the only locale so far, and the fallback for any other.

## How it is laid out

`packages/i18n/src/locales/en.ts` is the English catalog. Each top-level key is a namespace:

| Namespace | Used by                                                                            |
| --------- | ---------------------------------------------------------------------------------- |
| `common`  | The shell, navigation, the home page, route states, the "could not confirm" notice |
| `auth`    | Sign-up, sign-in, email verification, password reset, field validation             |
| `profile` | The profile page and passkeys                                                      |
| `admin`   | The admin user list                                                                |
| `errors`  | A message for every server error code and the Better Auth codes the screens handle |
| `email`   | The verification and password reset emails                                         |

Keys are typed through i18next's `CustomTypeOptions`: `t("signIn.titel")` fails `bun run typecheck` with "Did you mean 'signIn.title'?". `packages/i18n/src/keys.types.test.ts` proves it stays that way.

ESLint's `i18next/no-literal-string` rule fails on a hard-coded string in a web or mobile component ([quality.md](quality.md#lint)). Keep every user-visible string, including button labels, `aria-label`s and page titles, in the catalog.

## Adding a string

1. Add the key to `en.ts` under the namespace of the screen that shows it. Use `{{name}}` for values.
2. In a component, `const { t } = useTranslation("profile")`, then `t("passkeys.added")` or `t("memberSince", { date })`. A component reading two namespaces calls `useTranslation` twice (`const { t: tError } = useTranslation("errors")`).
3. Values are not HTML-escaped by i18next (`escapeValue: false`): React escapes text it renders, and the email renderer escapes for itself. Never put a translated string into `dangerouslySetInnerHTML`.

### Error messages

`appErrorKey(code)` returns the `errors` key for an `AppError` code (`auth.unauthenticated` is `errors:auth.unauthenticated`), and `authErrorKey(code)` the key for a Better Auth code (`errors:betterAuth.INVALID_TOKEN`). Both fall back to `generic`. A test fails if a code in `ERROR_CODES` (`packages/contracts`) has no message, so adding an error code means adding its message. `errorMessageKey` in `@s10n-base/client/messages` picks the key for any failure a screen can meet, on the web and on mobile.

## Adding a locale

1. Copy `en.ts` to, say, `de.ts`, typed as `Catalog` so it must have the same shape, and translate the values.
2. Add it to `resources` in `packages/i18n/src/index.ts`: `{ en, de }`.
3. `bun run test`: a test fails until the new catalog has exactly English's keys.

`resolveLocale(codes)` picks the first supported language from a list of BCP 47 tags by its language subtag (`de-AT` matches `de`), and falls back to English. The web app passes `navigator.languages` to `createReactI18n`; the mobile app passes the device's locales from `expo-localization`. Emails are rendered in English for now; to send them in the user's language, store a locale on the user and pass it to `createTranslator("email", locale)`.

## The email namespace

`apps/server/src/auth/email/render.ts` renders each auth email from `email`: `verifyEmail.*` and `resetPassword.*` (subject, heading, body, action), plus `linkFallback`, `ignoreNotice` and `footer` (which takes `{{supportEmail}}`). `createTranslator("email")` is ready on return (`initAsync: false` with inline resources), so rendering needs no `await`. The text says the links work for one hour, matching `AUTH_EMAIL_LINK_SECONDS`; change both together.
