# 004: Auth

> Status: implemented on 2026-11-19, on branch `feature/001-strip-desktop-and-local-first` (PR #1, which carries the whole rework).

Phase 4 of [000](000-hosted-starter-rework.md). Builds on [003](003-hosted-server-core.md). Source labels such as `[S4]` are resolved in the private companion's README; nothing from that directory is copied into this repo.

## 1. Goal

A server that signs users up and in, with no UI yet (phase 5 web, phase 6 mobile):

- Better Auth mounted at `/api/auth` behind a Node-to-Fetch bridge and a route allow-list (D2).
- Email and password with verification, the `expo` plugin, the `admin` plugin and passkeys on by default (D3).
- Auth tables as our own migration, checked against Better Auth's schema.
- An app-owned session route and a session-backed caller for the RPC dispatcher.
- Email through our own SES v2 sender, and our own local capture server so the whole flow works on a fresh clone with no AWS account.

D2 and D3 are fixed. The organization plugin and social sign-in are documented recipes only.

## 5. Better Auth

`apps/server/src/auth/`.

### 5.1 Options builder

`buildAuthOptions(config, dependencies)` is a pure function with unit tests on its output. Project B has the smallest clean version to learn from `[S4]`; ours drops everything product-specific in it.

- `baseURL` from `APP_URL`, `basePath` `/api/auth`, the secret from config, telemetry off.
- Database: the Kysely adapter over the phase 3 `Kysely<DB>`, Postgres, snake casing, transactions on.
- Tables `ba_user`, `ba_session`, `ba_account`, `ba_verification`, `ba_rate_limit`, `ba_passkey`, with snake_case columns mapped explicitly and UUID ids generated by Better Auth's `uuid` setting.
- Email and password: enabled, verification required, verification email sent on sign-up and again on a sign-in attempt by an unverified user, sessions revoked on password reset, explicit expiry for both kinds of link.
- Rate limit: enabled, stored in the database (a memory store is wrong with more than one instance).
- Cookies: a neutral prefix from one constant; `httpOnly`, `sameSite: lax`, `secure` when `APP_URL` is `https`.
- Client IP: Better Auth reads it from one internal header that the bridge sets from the phase 3 client-IP resolver. An incoming copy of that header is stripped first.
- Trusted origins: `APP_URL`, the URL scheme of the server's `APP_VARIANT`, and `exp://` only when `NODE_ENV=development`.
- Plugins: `expo()`; `admin` with default role `user`, admin role `admin`; `passkey` with the relying-party id and origin from `APP_URL` and the name from the app name.
- `disabledPaths`: `/admin/remove-user`. Removing a user needs product-specific cleanup, so the stock endpoint stays off; `docs/auth.md` says how a project adds its own guarded version.
- Better Auth's logger routed into ours.

### 5.2 Migration

`migrations/001_auth.ts`, written by hand, as the first entry in the migration list: the six tables with `timestamptz` columns, `uuid` keys, foreign keys that cascade from the user (including sessions started by impersonation, which end with the admin who started them), a unique `(provider_id, account_id)`, and the indexes Better Auth's lookups need (session token, account by user, verification identifier, rate-limit key, passkey by user and by credential id).

A live test builds the auth instance, asks Better Auth for the schema it expects for this exact configuration, and compares tables, columns, types, nullability and uniqueness against the migrated database. It must fail when either side changes, so an upgrade that adds a column is caught. Then regenerate `generated/db.ts`.

### 5.3 Bridge and route guard

- **Bridge** (`http/fetch-bridge.ts`): converts the Node request to a Fetch `Request` whose URL is built from `APP_URL`, never from the `Host` header; reads the body through the phase 3 reader with its limit (413); copies the response back with every `Set-Cookie` preserved as a separate header; sets `Cache-Control: no-store`.
- **Route guard** (`auth/route-guard.ts`), following Project A `[S5]`: built from the auth instance's own endpoint inventory and matched with the `better-call` router, so our matching cannot disagree with Better Auth's. It runs before the body is read and before Better Auth sees the request, so a request for an unknown path cannot create a rate-limit row. Server-only endpoints and disabled paths are excluded.
- **Allow-list** (`auth/allowed-routes.ts`): a committed list of method and path pairs, each either exposed or deliberately not. The guard admits only inventory entries that are on the exposed list. A test fails when the inventory contains a route that is on neither list, so a Better Auth upgrade that adds an endpoint forces a decision.
- Anything else under `/api/auth` answers 404 JSON. CORS is extended only as far as the Better Auth web client needs (find out which methods and headers from its source and test them); the allowed origin is still only `APP_URL`.

### 5.4 App-owned routes and the RPC caller

- `packages/contracts`: `AppSession` (`userId`, `email`, `name`, `image`, `role`, `emailVerified`) and the response of the session route. This shape is ours and stays stable when Better Auth's changes.
- `GET /api/app-auth/session`: `{ok: true, data: {session}}` with `session` null when signed out; `no-store`.
- The dispatcher's `resolveActor` is replaced with a session lookup. Make it lazy: a `public` method must not cost a session query. A banned user or an expired session is `anonymous`.
- **Cross-site requests:** `/rpc` and `/api/app-auth/*` reject a request that carries an `Origin` header not on the trusted list (403), before any work is done. Requests with no `Origin` (mobile, server to server) pass this check and still need a session.
- `bun run auth:set-role <email> <role>`: a small entry that sets a user's role, so a project can create its first admin. It refuses unknown roles and unknown users.

## 6. Email

### 6.1 Sender

- `AuthEmailSender`: `sendVerificationEmail({to, url})` and `sendPasswordResetEmail({to, url})`. Better Auth's hooks call it; nothing else knows how email is delivered.
- Rendering in one module: subject, plain text and HTML for each kind, every interpolated value HTML-escaped, and a refusal to render a link that is not `http` or `https`. The English strings sit together in one file; phase 5 moves them into `packages/i18n`.
- **Our own SES v2 sender** (`infra/email/`), replacing the AWS SDK (owner decision in plan 000):
  - A SigV4 signer on `node:crypto`: canonical request, string to sign, the HMAC key chain, the session-token header when present.
  - `SendEmail` as one `fetch`: `POST /v2/email/outbound-emails` to `https://email.<region>.amazonaws.com` or `SES_ENDPOINT`, a timeout through `AbortSignal`, and the response's message id.
  - Retries on an Effect `Schedule`, bounded, only where the request was certainly not accepted: connection refused, throttling, 5xx. A timeout after the request was sent is not retried, because SES has no idempotency key and a retry could send twice.
  - Errors mapped to a small typed set (rejected address, not verified, throttled, credentials, unavailable). The log line never contains credentials or the signature.
  - Static access keys only. `docs/auth.md` says that a project needing role assumption, SSO or instance credentials puts the AWS SDK back behind `AuthEmailSender`.
- **Verify the signer against AWS's published SigV4 test vectors.** Plan 000's signing details and line estimate came from research, not from running code. Fetch the official suite, commit the vectors you use as fixtures with their source and licence noted, and make the signer pass them. If the official suite cannot be obtained, say so and do not substitute vectors computed by our own code.

### 6.2 Local capture server

`scripts/ses-local/`, on `node:http`, run with bun. About 120 lines plus tests. It replaces the emulator package all three projects use.

- `POST /v2/email/outbound-emails` (SES v2 JSON field names), `GET /store`, `GET /health-check`, `POST /clear-store`, and an inbox page at `/` that lists captured emails and shows each one's text with its links clickable. Everything rendered is escaped.
- It checks the request's SigV4 signature against the local placeholder credentials and answers 403 on a mismatch. That makes every local sign-up an end-to-end test of the signer.
- Binds to loopback only and refuses to start on any other address: the inbox is unauthenticated.
- A bounded store (oldest dropped), a body limit, and a loud 400 for raw MIME or template content, which we do not send.
- `bun run ses:local` starts it. `bun dev` starts it alongside Postgres, the server and web, and prints the inbox URL. `.env.example` points the server at it.

## 7. Tests

Unit tests come first for every module above. Live tests (`*.live.test.ts`, the phase 3 lane) start the capture server in-process and drive the real HTTP surface:

1. Sign up, read the verification email from `/store`, follow its link, sign in, `GET /api/app-auth/session` returns the `AppSession`, sign out, the session is gone.
2. Sign-in before verification is refused and sends another email.
3. Password reset: request, read the email, set a new password, old sessions are revoked, the old password no longer works.
4. Several `Set-Cookie` headers survive the bridge.
5. A request to an unknown `/api/auth` path is 404 and adds no rate-limit row; repeated bad sign-ins are limited and the rows are in the database.
6. `/admin/remove-user` is 404. An admin endpoint called by a `user` is refused; after `auth:set-role` it works.
7. RPC with fixture methods: a signed-in user passes `session`, fails `{role: "admin"}`; anonymous gets 401; a foreign `Origin` gets 403.
8. Passkeys: registration options are returned for a signed-in user and refused when signed out, and the table exists. The full ceremony needs an authenticator and is phase 7's.
9. The migration matches Better Auth's schema (5.2).

CI: the live step starts nothing extra (the capture server is in-process) and sets the new variables. The smoke test keeps passing with the new required variables.

The lockfile gained 43 packages (326 to 369 entries), most of them the passkey plugin's WebAuthn libraries (`@simplewebauthn/*`, `@peculiar/*`, `asn1js`, `tsyringe`) and Better Auth's adapter packages, which `better-auth` depends on even when unused. Kysely resolves to the one 0.29.9 the server already uses. `bun audit`: no vulnerabilities (330 packages). Nothing else was added: no AWS SDK, no emulator, no mail library.

### What Better Auth 1.7.25 required that the plan did not predict

- **It turns its origin and CSRF checks off when `NODE_ENV` is `test`** (`skipOriginCheck` defaults to `isTest()`; the CSRF check follows it). Under Vitest, which sets `NODE_ENV=test`, the first live run accepted a sign-in from `Origin: https://evil.example.com`. The options now set `advanced.disableOriginCheck: false` and `advanced.disableCSRFCheck: false`, and live tests show foreign-origin sign-ins and cookie-carrying requests refused with 403. Its own checks apply to a sign-in or sign-up that carries an `Origin` (or Fetch Metadata headers) and to any request carrying a cookie; a request with neither, as a native app or curl sends, is accepted.
- **The `casing` option is accepted by the type but not used.** No code in 1.7.25 reads it. Every column is mapped explicitly (`AUTH_TABLES` in `options.ts`), and `casing` is not passed.
- **With `generateId: "uuid"` on Postgres, Better Auth does not generate ids**: the Kysely adapter reports UUID support, so inserts omit the id and rely on the column default. The migration defaults every id to `gen_random_uuid()`.
- **`getSchema` keys fields by column name** once fields are mapped, and Better Auth's own migration planner (`getMigrations`) does not report an extra column or a text column of the wrong type (checked by mutating the migration). So the live schema test has its own comparison (`auth/schema-check.ts`) and also requires the planner to have nothing to do.
- **The passkey plugin's `userId` reference declares no delete rule**, and the admin plugin's `impersonatedBy` is a plain string with no reference. The migration cascades both from the user; the schema comparison records the second as our own choice (`OWN_CHOICES`).
- **The `expo` plugin adds `exp://` to the trusted origins by itself** when `process.env.NODE_ENV` is `development`, reading the process environment rather than our config. Our list has the same rule, so they agree.
- **Rate limits** are on only in production unless `enabled` is set (it is). The defaults are 3 per 10 seconds for sign-in, sign-up and change-password, 3 per 60 seconds for the email-sending routes, and 100 per 10 seconds elsewhere, per address and path. Postgres returns `last_request` (a `bigint`) as a string; Better Auth's arithmetic copes, and the live test shows limits working.
- **The Better Auth web client** sends only `GET` and `POST` with `content-type: application/json` and `credentials: "include"`, so CORS needed no change (section 5.3).
- `auth.api` exposes the whole inventory with `path` and `options.method`/`options.metadata.SERVER_ONLY`, so the guard needs no private API. Better Auth builds a new router per request in `auth.handler`; the guard builds one router at startup.

### SigV4 and the line estimates

- **Test vectors:** AWS's documentation no longer offers the suite (`aws-sig-v4-test-suite.zip` answers 404, and the test-suite page redirects to the IAM guide's introduction). The IAM guide's Signature Version 4 pages link to `awslabs/aws-c-auth`, which keeps the suite. Its 38 `v4` cases were fetched at commit `f556deacd6e6d9dbf540ff00a9bf383688076874` and committed unchanged, with `LICENSE` and `NOTICE` (Apache-2.0), in `apps/server/src/infra/email/sigv4-test-suite/`. Only the header-signing files were copied. **The signer matches all 38**: canonical request, string to sign, signature and `Authorization` header, including the path normalisation, query ordering and encoding, header folding and duplicates, the session token signed and added after signing, and the signed payload hash.
- **Details plan 000 left out:** outside S3 the canonical path is the encoding of the path as sent (so `/a%20b` is signed as `/a%2520b`); query parameters are decoded and encoded once; header values are trimmed with inner whitespace collapsed and repeats joined by commas.
- **Size:** the signer is about 150 lines of code plus a 70-line verifier for the capture server, and the SES client about 210, against plan 000's "about 150" for both. The capture server is about 250 lines of code against "about 120", most of it request validation and the inbox page.

### Departures from this plan, with reasons

- **Formatter exclusions.** `kysely-codegen --verify` compares the generated file byte for byte and oxfmt reformats it, so `generated/**` is excluded from oxfmt; the SigV4 fixtures are excluded so they stay as published. `plans/` stays excluded.
- **The capture server imports the signer from `apps/server`**, and the server's `tsconfig.json` includes `scripts/ses-local/server.ts`, so the live tests can start it in-process. One signer serves both; the AWS vectors keep it honest, so a bug cannot hide in a matching verifier.
- **`context.actor` became `context.getActor()`**, to make the lookup lazy (section 5.4): a public method costs no session query, and any handler looks the caller up at most once.
- **The cross-site check uses Better Auth's own origin matcher** (`(await auth.$context).isTrustedOrigin`), so `/rpc` and Better Auth agree on what is trusted.
- **Email links are Better Auth's own routes**: `/api/auth/verify-email?token=…` and `/api/auth/reset-password/<token>`, which redirects to the client's `redirectTo` with the token. With no web screens yet, these are what a user can follow. Phase 5 can point them at its own pages.
- **Replies go to `SUPPORT_EMAIL`** (`ReplyToAddresses`), since `EMAIL_FROM` is a no-reply address.
- **Retries:** besides a refused connection, a failed DNS lookup (`ENOTFOUND`, `EAI_AGAIN`) is retried, since nothing reached SES. `LimitExceededException` (a used-up quota) is "throttled" but not retried. A reset connection after sending is not retried. The default schedule is at most two retries, backing off from 250 ms with jitter.
- **Admin routes exposed:** list and get users, set role, ban and unban, list and end a user's sessions, and has-permission. Not exposed: create-user, update-user, set-user-password, impersonate and stop-impersonating. Each has its reason in `allowed-routes.ts`.
- **`auth:set-role`** is also built as `dist/set-role.mjs`, since a deployment needs its first admin too. It exits 2 for bad arguments and 1 for an unknown user.
- **CI** needed no change: the live and smoke steps read the new variables from `.env.example` through `scripts/with-env.ts`, like the phase 3 ones, and the capture server runs inside the test process.
- **Extra indexes** are allowed by the schema comparison (an index Better Auth expects must exist; one it does not expect, such as `ba_session.impersonated_by`'s, is fine). Everything else must match both ways.
- The capture server also checks the signature date (15 minutes either way, as AWS does) and keeps the last 200 emails with a 1 MB body limit.

### For later phases

- **Phase 5 (web, `packages/client`, `packages/i18n`):** the session route answers `{ok: true, data: {session}}` with `AppSession` from `contracts`. Sign-up should pass `callbackURL` (where the verification link lands) and password reset `redirectTo` (the page that receives `?token=`); both must be under `APP_URL`. The email text in `auth/email/text.ts` moves to `packages/i18n`. RPC handlers get the caller with `await context.getActor()`. The Better Auth client works with the current CORS and the Vite proxy. The profile's passkey management uses the exposed `/passkey/*` routes; the admin user list can use the exposed `/admin/list-users` or an RPC method, but a role check in RPC gives one place to audit.
- **Phase 6 (Expo):** the server trusts `<urlScheme>://` for its `APP_VARIANT` from `packages/shared/src/app-variants.ts`; extend that table with bundle ids rather than adding a second one. The Expo client sends `expo-origin`, which the `expo` plugin turns into `Origin` for Better Auth's checks; requests to `/rpc` without an `Origin` pass our check and need the session cookie the client stores. `exp://` is trusted only with `NODE_ENV=development`. The passkey relying-party id is `APP_URL`'s host, which matters for native passkeys.
- **Phase 7 (Playwright):** read emails from the capture server's `/store` and call `/clear-store` between tests. Rate limits are on in every environment and keyed by client address: a journey that signs in more than three times in ten seconds from one address gets 429, unless the server runs with `TRUSTED_PROXY_HOPS=1` and the test sends its own `X-Forwarded-For` (as the live tests do). For a virtual authenticator, the relying party is `localhost` with the default `APP_URL`. Better Auth's origin checks stay on under `NODE_ENV=test`, so the browser's `Origin` must be `APP_URL`.
- **Phase 8 (deployment):** production needs real SES keys, a verified `EMAIL_FROM` identity, `APP_VARIANT` and a generated `BETTER_AUTH_SECRET`; `dist/set-role.mjs` creates the first admin. The bundle keeps `better-auth` and its plugins external, so the image needs them in `node_modules`.
